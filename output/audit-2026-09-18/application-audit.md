# Tame Your Biz — application audit, September 18, 2026

## Conclusion

The application has useful, substantial SQLite and workflow infrastructure, but it is not yet a dependable multi-user business application. The largest problems are active identity/permission wiring, volatile inventory, incomplete business relationships, incorrect reporting, and missing end-to-end recovery/release evidence. Finishing more screens before these boundaries are settled would leave attractive controls resting on incomplete behavior.

This is an audit, not a repair or acceptance certificate. No production code, existing tests, blueprints, normal application database, or Maintainiac 5.7 files were changed. Audit-only probes and evidence are under this directory. Existing source edits were preserved. The full test suite regenerated tracked PDF previews under `output/pdf`, including preview files that were already dirty; their exact pre-audit bytes were not snapshotted. Those preexisting dirty previews were not reset to Git. This artifact side effect is separate from production-source changes. No other agent was delegated work. The “Migrate UILab to SQLite” conversation was read for context; its assertions were independently checked where reported below.

## Scope and evidence rules

Reviewed normal startup, account gateway, operational scope, directory/employee persistence, Work/financial models and transactions, report projections, receipt intake/storage, inventory mutations, document delivery, settings, native capability controls, platform configuration, and selected test implementations. Discovered 684 production Dart files, 378 test files and four device integration entry points. Discovery is not a claim that every line in all those files was manually reviewed.

Evidence levels in the ledger:

- **Reproduced:** an independent executable probe demonstrates the failure in synthetic data.
- **Source-confirmed:** an explicit current implementation establishes the behavior or missing connection.
- **Risk/unverified:** a concern whose actual failure, platform behavior or coverage is not established.
- **Recommendation/decision:** proposed product or engineering direction, not an approved owner decision.

`source-manifest.json` fingerprints the inspected source inventory; `verification-summary.json` records fresh execution results and limitations. Existing passing tests and prior audits are evidence only. This is a broad architecture/workflow/readiness audit, not an exhaustive security penetration test, a complete field-by-field catalog certification, or native acceptance on every target device.

## Highest-priority discrepancies

### AUD-01 — Critical: login does not establish business authority

**Source-confirmed.** `lib/main.dart` supplies an account gateway separately from application startup. `work_ui_lab_bootstrap.dart`, `directory_ui_lab_bootstrap.dart`, `workday_ui_lab_bootstrap.dart`, and expense policies still supply a fixed company/actor and development grants. `AccountIdentity` contains email/verification, not a stable account UID plus company membership. `expensePermissionsForView` changes capabilities based on Admin/Technician presentation mode.

Consequence: employee profile permission selections and Firebase sign-in do not establish the user-A/user-B isolation required by the owner. Domain guards are useful but can only enforce the authority supplied to them. A presentation switch must never manufacture authority.

Required correction: a single trusted active-company/actor policy, supporting deliberate local-owner operation and authenticated company membership where applicable; fail-closed routes, queries/counts, mutations, exports, attachment access, notifications and sync; recheck revocation during asynchronous work and clear restricted cached projections on account change. Separate compensation access from ordinary employee directory access. Verify direct route access and direct service calls, not just hidden controls.

### AUD-02 — Critical: inventory additions are not durable

**Reproduced.** Audit probe adds stock, closes the actual SQLite-backed Work session/database, reopens both, and reconstructs the application operations store. The new stock is absent. `PrototypeOperationsStore.updateInventoryStock`, `addMaterialCost`, and `addInventoryCategory` mutate in-memory lists. `InventoryItemEntryScreen` pops after the synchronous list mutation. There is no durable stock ledger in that path.

This remains a problem even if the entire reference catalog is removed. Custom items, stock locations, receiving, consumption, transfers, recounts, reversals, cost history and links to receipts/jobs need the existing SQLite transaction authority. Save success must follow a durable commit. Relevant job/expense effects must commit atomically and retries must not duplicate stock or spending.

### AUD-03 — Critical for affected debug installations: review loader deletes Work data

**Reproduced.** When the review marker is absent, `loadRequestedWorkExamples` deletes the organization's `work/%` records, revisions and drafts before creating review fixtures. The probe inserts a synthetic preexisting Work record and confirms it disappears. Normal startup invokes this loader in debug builds with `UI_LAB_REVIEW_EXAMPLES` defaulting to true.

This is conditional, not a claim that every launch deletes data: it applies to debug startup with the marker absent. Existing comments describe a previous owner-requested replacement. That historical request does not make a default startup deletion safe for new installations with real work. Review fixtures need an explicitly isolated demo installation and opt-in lifecycle. No normal application launch was performed during this audit.

### AUD-04 — High: report outstanding amounts ignore partial payments

**Reproduced.** A $100 invoice with a $40 recorded payment produces $100 outstanding in `PrototypeReportProjection` instead of $60. Outstanding/overdue sources use `_workSource`, which copies the original invoice total. Payment collections are summed separately. Other screens calculate remaining balance differently, creating inconsistent business figures.

Use one authorized invoice-balance projection everywhere, reconciling issued amount, payments and future corrections. Separately define period activity versus balance “as of” a date: the current projection filters outstanding invoices by issue date, so older unpaid invoices fall outside a selected period. The latter behavior requires explicit labeling or a corrected receivables basis.

### AUD-05 — High: names still act as record relationships

**Reproduced for employee reports; source-confirmed for customer links.** Employee expense filtering checks `record.owner == employeeName`. An expense with another employee's stable ID but the same display name appears in the requested employee report. This demonstrates an attribution defect, not proof of a separately authenticated cross-account exploit.

`CustomerDetailScreen` joins Work by customer name. `deliverWorkPdf` selects a customer by name; `WorkRecord` stores `client` text without a customer ID. Name changes or duplicate names can detach/mix history or select the wrong current customer details. Use stable company-scoped IDs, with display snapshots where historical documents require them. Existing Job assignment validation already demonstrates the better pattern: saved employee IDs and active-profile checks.

### AUD-06 — High: category search and reporting disagree

**Source-confirmed search gap; reproduced reporting gap.** `ReceiptCategoryPickerScreen` searches only the category label. No custom-category entry exists there; the category identity is a fixed enum. The picker exposes receipt-specific category IDs while report groups use older vehicle IDs. A $10 Charging Fees expense contributes $0 to the report's fuel/vehicle total and falls into other expenses.

Required work is a coherent category system, not just adding strings to one widget: durable stable IDs, standard categories plus company custom categories, aliases/common spelling variations, duplicate-name handling, archival without breaking old expenses, recovery/permissions, and shared report grouping. Search should offer suggestions without silently changing the selected category. Fuel must not be assumed exclusively vehicle-related. Custom categories must not imply tax treatment.

### AUD-07 — High: employee profiles are not an earnings system

**Source-confirmed.** Employee profile identity and SQLite save/revision handling exist, but `pay` is a free-text string. No structured salary/hourly basis, effective-dated rates, compensation permissions, approved timesheet period or gross-earnings calculation was located. `WorkdayAccess` still hard-codes two employee IDs and three vehicle IDs, so creating a new employee does not itself connect that person to an authorized timekeeping session.

The existing `StoredWorkdayRecord` is useful: UTC instants, employee ID, pause duration in microseconds, and precise elapsed duration. Preserve that accuracy; do not rebuild it as rounded decimal-hour buckets. It also requires a vehicle/odometer context, which is not appropriate as the only clock-in model for office/shop staff. An Employee Hours workflow needs employee-linked time entries independent of mandatory vehicle use, corrections with history, week boundaries/timezone rules, own-versus-company views, and rate history. Salary allocation and overtime/paid-break treatment remain product/policy decisions; do not invent them or call estimated earnings payroll. Payroll tax/withholding and QuickBooks integration remain outside current authorized implementation.

### AUD-08 — High: backup/restore services are not a usable backup product

**Source-confirmed.** SQLite snapshots, attachment manifests, candidate restore, integrity verification and application-switch services exist. Settings exposes “Saved work” but “Backup and company sync” is a noninteractive tile. Firebase gateway handles accounts, not business-record upload/sync. Firebase initialization currently supports Android/iOS; desktop account connection is explicitly unavailable.

Remaining work: user-visible protected backup/export and restore selection/review/retry; actual scheduled/cloud transport if retained in release scope; restore on a replacement device; attachment completeness; encrypted sensitive exports and access/key-recovery design; authoritative upload acknowledgments, conflict handling, account revocation and multi-device tests. A local change outbox is not a completed sync service. Do not advertise current account configuration as backup.

### AUD-09 — High: issued document history can change when directory data changes

**Source-confirmed.** Work PDF delivery builds from the current company profile and a customer found by current name. An immutable `GeneratedDocumentSnapshot` class exists, but no application use was found outside its definition. Export-attempt history is useful but does not retain the exact bytes/branding/address originally issued.

Persist an issuance revision with customer/company/terms/template snapshots and the exact retained artifact/hash. Reopening an issued copy must not regenerate a different historical document from today's directory. Draft preview remains distinct from issue/share; native handoff is not proof of delivery.

### AUD-10 — High: financial lifecycle is incomplete

**Source-confirmed.** The financial event enum contains invoice-issued and payment-received only; positive payment validation rejects overpayment and has useful balance checks. A durable refund/reversal/customer-credit event workflow was not found. Work lifecycle lacks explicit cancelled/void statuses. Work amounts still include floating-point totals, while Expenses has stronger exact decimal/minor-unit machinery; common currency ownership is incomplete across these models.

Required: shared exact arithmetic/basis, explicit correction/void/refund/credit semantics, deposits and allocation rules where supported, and no duplicate financial effect when an expense is linked to a job or materials. Existing guards should be preserved. This is not a proposal to calculate taxes or build a general ledger. “Invoiced minus recorded expenses” currently appears as estimated gross profit; it is not a complete profitability measure when labor, overhead and allocations are missing.

### AUD-11 — High: receipt-to-inventory is not complete

**Source-confirmed.** Expense save paths reject `prepareMaterialsReview` rather than commit stock; no production `InventoryParser` call was found under `lib`. Job material drafts can retain source-stock information but do not implement an atomic stock-consumption ledger. This prevents treating a successful parser test or material picker as a completed receipt-to-stock workflow.

Keep receipt saving independent of optional inventory. Recognition and parser output remain proposals. Explicit user review must decide items, quantities, units, costs, location and stock effects. Keep one original expense and source links; job allocation and customer charges are different facts. Parser implementation is reserved for the owner's separate effort; no parser changes were made here.

### AUD-12 — High: low-storage admission and receipt-file collision safety remain gaps

**Source-confirmed absence/risk; no physical disk-failure reproduction in this audit.** The storage conversation identified low-space warning/reserve work as unfinished. Current runtime-capability code handles memory/thermal/power but no shared free-disk/reserve admission gate was found in the searched native and Dart storage paths.

Receipt retention verifies/hash-checks and flushes a temporary file, which is good. `_copyEvidence` nevertheless deletes an existing final target before rename. Deterministic evidence identity plus repeated imports/retries deserves a targeted collision/failure test; do not treat the delete-before-publish sequence as proven safe. `_mergeEvidence` can also fail after earlier files were copied, requiring an orphan/cleanup policy that preserves referenced evidence. The shared attachment store uses unique identities and a different pattern. Unify safe file publication semantics, keep SQLite error handling even after a free-space check, and avoid promising that any fixed reserve guarantees successful writes.

### AUD-13 — High: current regression baseline is failing

Fresh analyzer and full-suite details are in `verification-summary.json`, `test-failures.json` and raw logs. The parser contract test contains a compile-time constant-expression error; it does not execute its intended scenarios. Other failures must be classified as behavioral defects, stale test expectations, or broken fixtures one by one. A known failure must not be dismissed merely because it also failed historically.

Existing tests were audited for intent: the catalog conversion suite compares input payloads to stored payloads, not product truth; the report projection fixture does not exercise the partial-payment balance defect; storage process-kill tests genuinely use disposable databases, kill an uncommitted writer and verify previously acknowledged values. Good infrastructure and incomplete business coverage coexist.

## What is worth preserving

- SQLite/Drift is the normal persistent authority for major confirmed domains. File evidence is not a competing business database; compatibility JSON constructors alone do not prove they are used at startup.
- The local store commits current records, retained revisions, command identity and outbox entry in one transaction, with revision checks and command fingerprints.
- File-backed SQLite requires WAL/FULL synchronization and foreign-key enforcement, verifies integrity, and refuses unsupported schema upgrades. That is a foundation, not proof of a future schema migration.
- Draft sessions/recovery, stale-editor rejection, atomic draft consumption and isolated storage-test helpers are substantial reusable work.
- Workday time preserves precise duration. Employee profiles already have stable IDs. Saved active employee assignment is validated against SQLite.
- Expense exact quantities/prices/minor-unit types and explicit evidence/draft handling should be reused across financial work.
- PDF export distinguishes cancellation, failure and handoff; export attempts have audit records.
- Device workload admission conservatively handles unknown capacity and prevents overlapping heavy work.
- Receipt text editing now uses `ReceiptTextEditingSession` with update/flush/retry/discard handling. Older audit statements describing only an in-memory text controller are stale and must not be repeated as current findings.

## What would make this app genuinely useful

These are recommendations, not additional approved scope.

A small business needs reliable answers to: What must happen today? Who is responsible? What was done? What did it cost? What has been billed? What has actually been paid? What is still owed? Can I find the original evidence and recover my work?

Build these as connected complete workflows:

1. **Set up the business and people.** Clear local-owner start, real company identity, durable customers/sites, employees and optional vehicles/equipment; capability-based access and offboarding without deleting history.
2. **Customer → estimate → approved work → job.** Stable customer/site links, versioned scope/acceptance, assignment, visit schedule, on-site notes/photos, actual activity and completion. Avoid retyping the same information at every stage.
3. **Job → invoice → recorded payment → follow-up.** Show exact outstanding balances, partial payments, corrections and evidence. Customer communication must show whether the action saved a file, opened another app or actually received an acknowledgment.
4. **Expense → evidence → optional allocation.** Easy manual entry first; familiar category search and custom categories; photo/import/reopen; optional job/material association without duplicate expenses. Keep incomplete proposals distinguishable from confirmed spending.
5. **Employee Hours.** Worker sees their own week; owner sees authorized people and gross-earnings estimates with historical rate basis. Keep hours, earnings, amounts billed for labor and actual payments distinct. Salary/policy decisions must be resolved before calculations are represented as final.
6. **Optional basic inventory.** User-created items, units/pack sizes, locations, receiving/use/transfer/count correction, low-stock thresholds and history. No curated catalog is necessary to make this useful. A parser can propose matches against the business's own items and reviewed aliases; unmatched lines stay reviewable. Removing a catalog must not remove raw source/evidence needed to understand earlier migrations.
7. **A truthful business recap.** Separate invoiced, collected, spent, outstanding and overdue. Show selected period and basis. Job margin requires complete cost allocations, not an unexplained “profit” number. Selecting a total opens its authorized source records.
8. **Recovery that ordinary people can operate.** Visible save/error/retry states, unfinished-work recovery, understandable backup status and a tested restore to a different installation. Offline workflows should remain usable when optional network services fail.

### Recommended Materials layout without committing to a catalog

Make “My inventory” the primary workspace. Put search, location, low-stock filters and Add item/Receive/Use/Transfer/Count actions near the records. On phones show the facts needed to act: item, size/unit, quantity, location and low-stock state. On wide screens use a bounded list/table with a selected-item details/history lane and a purposeful filter/location lane. Keep costs permission-controlled. A future reference catalog can be an optional picker, not the organizing foundation of the whole module. This is a proposal for owner review, not visual acceptance or an implemented redesign.

## Recommended correction order and acceptance gates

1. **Preserve and isolate real data.** Disable destructive review initialization outside explicit demo installations; retain a verified snapshot before repairs. Freeze source evidence and classify current test failures.
2. **Bind identity and protect private records.** Account-free local owner plus actual employee/company authority, dynamic employee linkage, compensation separation, account-switch/revocation tests. Do this before expanding salaries or team reporting.
3. **Repair numerical and relationship truth.** Shared balances, stable customer/employee IDs, consistent categories, exact arithmetic and history-preserving documents. Independent examples must include duplicate names, renames, partial payments and historical rates.
4. **Close durable workflows.** Complete Inventory SQLite commands and receipt/job relationships; prove restart, replay, stale revision, failure rollback and no duplicate financial effect.
5. **Deliver Employee Hours and recap against those foundations.** Resolve salary/break/overtime/reporting-basis choices, then persist calculations and corrections with appropriate access and export boundaries.
6. **Complete backup/sync and remaining modules in bounded slices.** Keep parser work separate but specify a shared proposal contract. Maintenance/scheduling/quotes should not be declared delivered by placeholder routes.
7. **Native and release validation.** Isolated account-A/account-B exercises; Android/iOS/desktop, one emulator at a time, real camera/file/share failures, restart/termination, backup restoration, large text and keyboard/screen-reader use. Do not test destructive scenarios against the owner's normal installation.

## Fresh test-quality observations

- Notification tests still expect the former Maintainiac brand while the adapter returns Tame Your Biz. This is a demonstrably stale wording expectation, not evidence that notification privacy works or fails.
- A calendar source-contract test opens a removed `inventory_widgets.dart` file. The test itself needs updating to the current ownership boundary without weakening the intended contract.
- Work responsive tests expect two “Not connected” labels but find one; this mismatch is not by itself proof of a responsive overflow.
- The expense-card accessibility case reports a 307-pixel bottom overflow at 320 logical pixels with 2x text. Its isolated non-scrolling fixture should be compared with actual list parents before assigning the complete production impact. The assertion failure is retained, not dismissed.
- Several job/estimate tests fail on missing widgets before they reach saving or stock assertions. They provide no current evidence of those later behaviors.
- The catalog parser contract cannot compile. It exercises an isolated legacy extraction, not the production receipt flow. The analyzer's single error is not a count of all compiler diagnostics; see its failed-suite logs for the complete failure.
- A line-count test reports files over 500 lines. This is a maintainability finding, not a reason to mechanically split working code; the owner's functionality-first exception applies.
- Some tests write tracked PDF outputs. Test artifact destinations should be isolated, or existing previews backed up, so future regression runs cannot overwrite unrelated review artifacts.
