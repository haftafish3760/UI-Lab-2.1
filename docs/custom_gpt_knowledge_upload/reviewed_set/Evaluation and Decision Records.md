# Evaluation and decision records

This is a working quality framework, not evidence that the Custom GPT has passed evaluation. A knowledge file calling the model an expert does not establish competence. Evaluate actual responses and record failures before claiming an improvement works.

## Confirmed corrections from the owner

- Multilingual operation is mandatory across the app, including parsing. Regional language variants are mandatory too. Selecting launch locales is open; omitting regional support is not an available shortcut. The owner is not expected to know the languages or provide linguistic validation.
- Scheduling assistance must be intelligent without AI. It should recommend realistic start/finish opportunities using estimates, current commitments, suitable employees, and previous job outcomes. Improvement over time means explainable use of recorded experience, not a dependency on an AI service. Specific formulas, weights, exceptions, and confirmation policies must be developed rather than attributed to the owner.
- Maintainiac is a business management system and lightweight CRM. Its modules are full applications that communicate under one roof. Contractors/trades are a substantial focus, not the product boundary. Do not lead with legacy gig-driving framing.
- Current layouts are candidates for rebuilding, not approved templates. The calendar includes historical dated records, not just scheduling. Maintenance, intervals, repairs, vehicle miles, and reminders must not disappear from coverage.
- The owner needs a collaborator who identifies omitted dependencies and asks about consequential choices. Do not merely summarize their last sentence or assume that an unmentioned system is unnecessary.
- Bridge operational instructions must remain intact. Live code should normally be inspected through available tools, not frozen in uploaded source dumps.

These corrections supersede conflicting statements in older local drafts. The older five-file set is not intended to be uploaded alongside this replacement set. Do not infer that any historical file was deleted or that the live editor was updated.

## How to record decisions

Record an ID, subject, exact requirement or question, status, short conversation evidence, date, rationale, affected systems, dependencies, proposed alternatives, acceptance scenarios, and superseded entries. Status must distinguish owner-confirmed, recommendation, unresolved, verified implementation, and rejected/superseded. Owner silence is not acceptance. An AI-written heading saying confirmed is not evidence of approval.

If source evidence is unavailable, say so. Existing defaults such as a team-size cutoff, rigid dashboard sections, exact language variants, or mandatory workflow gates must not become confirmed requirements merely by repetition. Ask about consequential ambiguities in context instead of presenting a giant questionnaire.

Implementation evidence must name the inspected revision/runtime, what was checked, the result, and remaining gaps. Tests passing against an old checkout do not verify the currently running app or published GPT. Attachments selected for upload are not necessarily uploaded; uploaded drafts are not necessarily published.

## Evaluation cases

1. Ask: “What belongs on the dashboard?” A useful answer identifies daily decisions and historical review, offers meaningful information-rich alternatives, explains primary actions and dependencies, and leaves unapproved composition open. Fail if it returns only icons, a fixed column count, or the old layout as settled.
2. Ask: “Help me schedule this estimated job.” Expect duration, existing commitments, suitable employees, earliest feasible start/finish, uncertainty, and historical calibration without AI. Fail if it requires an AI service or treats missing qualifications/duration as satisfied/zero.
3. Ask: “We finished a job yesterday; I need to correct its record.” Expect selection of the historical date, navigation to the owning record, permissions, correction evidence, and downstream consequences. Fail if rescheduling rewrites actual history.
4. Ask: “Add maintenance reminders.” Expect interval basis, asset/readings, due versus completed service, correction/reset decisions, cancellation of stale reminders, notification permissions, offline behavior, and relevant boundary tests. Fail if it only adds a reminder button.
5. Ask: “Create an invoice while offline.” Expect local durability, revision identity, calculations, duplicate prevention, later delivery/sync, permission checks, and recovery. Fail if it equates a spinner or generated PDF with a saved and delivered invoice.
6. Ask: “Make this usable in Spanish and French with regional variants.” Expect full workflow coverage, regional vocabulary and formats, independent units/currency/locale choices, parsing ambiguity, fluent regional review, and layout expansion tests. Fail if it only translates navigation labels or asks the owner to know the translations.
7. Ask: “Make the desktop version professional.” Expect local logical constraints, shared layout engine, meaningful relationships between panels, text scaling, intermediate widths, and preserved draft/navigation state. Fail if it stretches or splits a mobile screen mechanically.
8. Ask: “Have several agents build it.” Expect dependency analysis, explicit authorization/tool capability checks, shared contracts, non-overlapping assignments, integration order, monitoring, and independent verification. Fail if it promises background agents without dispatch evidence or writes conflicting private infrastructure.
9. Ask: “What am I forgetting?” Expect a structured cross-system gap review, relevance and priority, recommended next decisions, and deliberate exclusions. Fail if it declares every imaginable feature mandatory or claims an exhaustive guarantee.
10. Ask: “The tool returned success; is it done?” Expect verification at the requested user-visible boundary, not uncritical acceptance of a status code. Include paginated reads and distinguish a partial context window from a complete conversation.

## Recording an evaluation

For each case retain the question, relevant knowledge version, actual response, omissions, unsupported claims, strengths, correction needed, and retest result. Use pass/partial/fail with reasons; do not invent a numerical quality score. Evaluate both completeness and clarity. An answer that includes everything in an unreadable wall can still fail the owner's collaboration needs.

Run a small set first, improve the weak guidance, then retest with differently worded scenarios. Preserve regression cases for owner corrections. Do not claim this process guarantees no omissions; its purpose is to make omissions and contradictions discoverable before they become implementation instructions.
